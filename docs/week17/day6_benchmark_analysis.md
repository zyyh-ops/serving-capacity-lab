### 1.3 客户端负载定义（`experiments/day6_suite.sh`）

| 项 | 值 |
|---|---|
| 接口 | `POST http://127.0.0.1:8000/v1/completions`（OpenAI 兼容），流式（`no_stream=False`） |
| 数据集 | `--dataset-name random`，`--random-range-ratio 0.0` → 定长 |
| workload | `short_decode`: 64 in / 128 out；`balanced`: 256 in / 128 out；`long_prefill`: 512 in / 32 out |
| 采样 | `--seed 2026 --ignore-eos`；`temperature` 未设（走 server 默认） |
| 请求数 | 128 / 组（`DAY6_NUM_PROMPTS` 未使用） |
| 指标 | `--percentile-metrics ttft,tpot,itl,e2el`，`--metric-percentiles 50,95,99` |
| SLO | `--goodput ttft:200 tpot:15` |
| A 组（concurrency） | `--request-rate inf --max-concurrency C`：**无限速发起 + 客户端信号量限流**，C 个协程跑完立刻补位 → 零思考时间的**闭环** |
| B 组（rate） | `--request-rate λ --burstiness 1.0`，**不设** `--max-concurrency` → Poisson 到达的**开环** |

两个语义细节（都来自源码，不是约定俗成）：

1. `--request-rate inf` 时 `get_request()` 给每个请求的间隔都置 0（`vllm/benchmarks/serve.py:171-172`），所以 128 个协程是一次性全部创建的；真正的背压来自 `asyncio.Semaphore(max_concurrency)`（`serve.py:512-523`）和 aiohttp 连接池上限（`serve.py:411-414`）。因此 A 组是「C 个用户、零思考时间」的闭环，**不是**突发压测。
2. 有限速率时，间隔从 `Gamma(shape=burstiness, scale=1/(λ·burstiness))` 采样（`serve.py:174-178`），`burstiness=1` 即指数分布 → Poisson。随后把累计间隔**整体缩放**，使最后一个请求恰好落在 `N/λ`（`serve.py:183-196`）—— 这保证不同 seed 下总到达窗口一致，也让我们可以用 `N/λ` 反算时长（§2.3）。

### 1.4 指标定义（以本仓库 vLLM 源码为准）

| 指标 | 定义 | 源码 |
|---|---|---|
| TTFT | 请求发出 → 第一个 content chunk 到达的客户端时间（含 HTTP、排队、tokenize、prefill、首 token 采样） | `serve.py:306`（`ttfts.append(outputs[i].ttft)`） |
| ITL | 相邻两个流式 chunk 的间隔；按请求收集后拼成一个大列表 | `serve.py:305` |
| TPOT | `(latency − ttft) / (output_len − 1)`，**每请求的平均每 token 时间**，排除首 token | `serve.py:298-304` |
| E2EL | 请求发出到流式结束的整段耗时 | `serve.py:307` |
| Request throughput | `completed / benchmark_duration` | `serve.py:343` |
| Output token throughput | `Σ output_len / duration` | `serve.py:345` |
| Total token throughput | `(Σ input + Σ output) / duration` | `serve.py:346` |
| **Goodput** | `满足全部 SLO 的请求数 / duration`，逐请求判 `all(SLO ≥ metric)` | `serve.py:312-332`、`344` |
| duration | 从第一个请求入队到 `asyncio.gather` 全部结束（含到达间隔与尾部 drain） | `serve.py:525`、`583` |

三个容易踩的口径：

- **TPOT 是「每请求平均」，不是尾部**。一个请求里出现两次 13 ms 的 ITL 尖峰，TPOT 仍可能只有 5 ms（§3.3 会量化）。
- 服务端的 `vllm:time_per_output_token_seconds` 直方图实际喂的是 **ITL 值**（`vllm/v1/metrics/loggers.py:555-557`），和客户端的 TPOT 不是同一个东西，不能混用。
- `request_goodput` 是**速率**（good/s），不是比例；同一「达标率」在不同 duration 下会给出不同的 goodput（§5.3 的 C=2 / C=4 就是这个现象）。

### 2.3 两个恒等式（用来证明负载模型真的按设计生效）

**(a) 闭环：`duration ≈ N·W/C`**

| 运行 | `128 × mean_e2e / C` | 实测 duration | 误差 |
|---|---|---|---|
| C=1 | 65.79 s | 65.84 s | −0.08% |
| C=2 | 36.85 s | 36.90 s | −0.12% |
| C=4 | 18.84 s | 18.86 s | −0.09% |
| C=8 | 10.04 s | 10.07 s | −0.23% |
| C=16 | 5.02 s | 5.04 s | −0.31% |
| C=32 | 2.80 s | 2.83 s | −0.99% |
| C=8 balanced | 10.40 s | 10.41 s | −0.13% |
| C=8 long_prefill | 3.95 s | 3.98 s | −0.64% |

误差随 C 增大（0.1%→1.0%），因为运行越短，客户端的启动/收尾开销占比越大；但仍在 1% 量级 ⇒ **整段测试里确实恒有 C 个请求在途**。

**(b) 开环：`duration ≈ N/λ + W_tail`**

| 运行 | `128/λ + mean_e2e` | 实测 duration | 误差 |
|---|---|---|---|
| r=2 | 64.59 s | 64.59 s | 0.00% |
| r=5 | 26.23 s | 26.19 s | −0.15% |
| r=10 | 13.46 s | 13.41 s | −0.43% |
| r=20 | 7.16 s | 7.03 s | −1.8% |

⇒ 到达过程确实是「按 λ 均匀铺开 + 尾部 drain」，不是「一次性全发」。

### 2.4 固定长度与可复现性

`short_decode` 的 6 组 + 4 组 rate 的 `total_input_tokens`/`total_output_tokens` **完全一致**（8,189 / 16,384），说明 `--seed 2026 --random-range-ratio 0.0` 让 128 条 prompt 逐条相同。`input_lens` 的分布是 **63×3 + 64×125 = 8,189**（不是 8,192），这是 random 数据集 decode→re-encode 后的长度量化，不是丢请求；`balanced` 是 32,737（123×256 + 3×255 + 232 + 252），`long_prefill` 是 65,461（123×512 + 509 + 507 + 504 + 503 + 462）。输出侧全部正好是目标长度（`--ignore-eos` 生效）。

### 3.2 TTFT：一次台阶 + 随 batch 爬升

| 运行 | 在途 | TTFT p50 | <18 ms 占比 | E2EL p50 |

**观测**：

1. **第一次跳变**发生在「从 0 个在途到 1 个在途」：C=1 的 TTFT 只有一个峰（12.97 ms），C≥2 立刻分成 ~13 ms 和 ~24–26 ms 两簇。低于 18 ms 的比例从 91% 掉到 0–17%（C≥8 时是 **0**），说明**prefill 一旦与 decode 合批，就要多付约 11 ms**。
2. **第二次爬升**发生在高并发：C=4→C=32，TTFT p50 从 25.9 涨到 58.9 ms，p95 从 38.0 涨到 109.8 ms。这主要不是稳态排队（§6.3 的 waiting 均值基本为 0），而是两件事叠加：
   - 一个 step 里 decode 的条数 B 越多，step 越长（5.0 ms @ B=32），到达的请求平均要等**半个 step**；
   - 启动瞬间 C 个请求同时到达，`C×64` 个 prefill token 远超 512 的 token budget，只能按 **8 条/步** 分批（`scheduler.py:196,206-298,333-338`）——C=32 的首批请求最多要等 3 个 prefill 批次。
   C=8/16/32 的 p95（49.9 / 63.3 / 109.8）与「启动 prefill 需要 ceil(C/8) 个批次」（1 / 2 / 4）同向增长，与这条机制吻合（等级 B，但无法把两个因素拆开定量）。
3. **开环的 TTFT 明显更平**：r=2→r=20，在途从 1.16 涨到 13.70，TTFT p50 只从 24.07 到 27.50（+14%）。因为 Poisson 到达是「细水长流」，不会出现「C 个请求同时 prefill」的启动批；这也说明 **TTFT 主要由到达模式决定，而不是由在途数决定**。
4. p99 波动大（C=4 44.94、long_prefill 117.68），因为 128 个样本时 **p99 就是第 2 名的值**（`ceil(0.99×128)=127`），单个慢请求即可改写。

- **batch 32 的 TPOT 只比 batch 1 高 27%**（5.01 vs 3.93 ms），却每步产出 32 个 token ⇒ 这是整份报告最重要的一条：0.6B + 4090 在 decode 阶段有巨大的算力冗余，扩大 batch 几乎只增加一点点时间。
- 从 1→32 的增量约 **0.035 ms/seq**（(5.01−3.93)/31），远小于 day5 launch-bound 时代的 14.6 ms/step。**此时瓶颈已经不是 launch**，而是每步固定的 ~4 ms 开销（28 层 × (GEMV + attention + 归一化) + 采样）。
- **r=20 的 TPOT（5.73 @ L=13.7）反而高于 C=16（4.61 @ L=16）**，差 24%，而两者在途数相近。这不是排队（waiting=0），最可能是**batch 组成**不同：Poisson 到达下每个 step 的 batch 在 8–20 之间抖动，prefill 与 decode 的混合比例也在变；单次运行无法把「运行间抖动」拆出去（§7 #8）。

**逐间隔分桶（占比 %）**：

| C=8 | 4.76 | 2.40 | 1.58 | 1.08 | 25.41 |
| C=16 | 3.35 | 2.14 | 1.80 | 0.88 | 18.73 |

| C=8 balanced | 3.88 | 2.88 | 2.31 | 1.25 | 25.56 |
| **C=8 long_prefill** | **28.06** | **13.03** | **12.27** | **7.35** | 20.99 |
| r=2 | 3.19 | 2.15 | 1.35 | 1.13 | 33.48 |

| **r=20** | **15.09** | **10.88** | **10.41** | **9.45** | 21.89 |

三条结论：

1. **long_prefill 是全场最差的 ITL 分布**：28% 的间隔 >6 ms，7.35% >12 ms。机制是结构性的——512-token prompt 在 8 条 decode 占掉 8 个 token 后只剩 504 的预算，必须**分两块**做（`scheduler.py:196,218`）；每个 prefill chunk 所在的那一步处理约 504+8 个 token，远慢于 4.7 ms 的纯 decode 步，于是所有在途请求的那一个 token 都被推迟。§6.3 里 long_prefill 的 waiting 峰值 3 也是同一个原因。
2. **r=20 比 C=32 的尾巴更差（p95 13.04 vs 6.94），尽管在途只有 32 的一半**。说明「ITL 尾部 ∝ 在途数」是错的：Poisson 到达下 prefill 插入的时刻更随机、batch 组成更抖，尾部反而更差。闭环在 C=32 时虽然 batch 更大，但到达被完成事件「节拍化」，每个 step 的组成稳定。
3. **低并发下的 8–10 ms 簇**（C=1 就有 1.9% >6 ms）还有第二个来源：**流式 chunk 合并**。ITL 条目数只有 124–127（应为 127），但 `ΣITL` 与 `E2E−TTFT` 逐请求完全相等（附录 A），说明时间没漏记，而是「一次到达带 2 个 token、只记一个间隔」。chunk 合并与 prefill 插入在客户端数据里**不可区分**，这是本报告最硬的一个测量局限。

结论：**TPOT 适合回答「平均每 token 多快」，ITL p95/p99 适合回答「卡不卡」**。r=20 的 TPOT p95 是 6.07 ms，而 ITL p95 是 13.04 ms —— 差 2.15×，这是同一批数据里最大的口径差异。

## 5. Goodput

### 5.1 口径

`--goodput ttft:200 tpot:15` ⇒ 逐请求判断 `TTFT ≤ 200 ms` **且** `TPOT ≤ 15 ms`，`goodput = 达标请求数 / duration`（`serve.py:312-332,344`）。注意：

- 用的是 **TPOT（每请求平均）**，不是 ITL 尾部；
- 分母是整段 duration（含到达间隔与 drain），所以它是**速率**；
- 未达标请求仍计入 `completed` 与吞吐，只是不计入 goodput。

### 5.2 实测：12 组全部 goodput ≡ throughput

12 组的 `request_goodput` 与 `request_throughput` **逐位相等**，重算也得到 128/128 全达标、0 个 TTFT 违规、0 个 TPOT 违规：

### 5.4 为什么这套 SLO 不会被违反

- TPOT 的上界受 `max-num-seqs=32` 约束：L=32 时 TPOT 5.01 ms（把启动/收尾也算上的有效步长 5.52 ms），即使再翻倍也很难到 15 ms。
- TTFT 要 >200 ms，需要 ~150 ms 以上的排队；本次最差单请求 125 ms（long_prefill 的 512-token prefill 本身就要 60 ms + 分块等待），仍在 200 以内。
- 因此本配置下，**只要不把 `max-num-seqs` 调到 64+ 或把 prompt 拉到接近 `max-model-len`，这套 SLO 几乎不可能被违反**。想用 goodput 定位拐点，必须换更严的 SLO（如 50/6 或 30/5，见 §5.3）或换更长的 prompt。

- `num_requests_running` = 「**在模型执行批次里的请求数**」（`:188-195`），不含还在 tokenize/HTTP 层的请求；

- `gpu_cache_usage_perc` = `1 − free_blocks/total_blocks`，**按块计**（`vllm/v1/core/block_pool.py:307-318`），是 `kv_cache_usage_perc` 的废弃别名；

- 两个 token counter 在**每次 iteration**按 `IterationStats` 累加（`:538-543`）。

### 6.3 Running / Waiting：负载确实打进去了，但排队只出现在 long_prefill

- **峰值 running 与配置逐点吻合**：C=1/2/4/8/16/32 → 1/2/4/8/16/32，说明客户端信号量限流生效、服务端真的同时执行了这么多请求。**C=32 的峰值 32 说明 `max_num_seqs ≥ 32`；按 README 的 32，这就是本日唯一触到 seq 天花板的点**（详见 §1.2 的可验证性说明）。
- **开环峰值高于在途均值**（r=2 峰值 6、r=10 峰值 11、r=20 峰值 20），是 Poisson 突发叠加 0.5 s 采样的结果；这些瞬时值只能当「曾经达到过」，不能当稳态。
- **waiting 在 10/12 组里恒为 0**；两个例外：
  - `C=16`：峰值 1、均值 0.09、8.9% 的活跃时间 >0。最可能是**启动瞬间** 16 个 prefill（1,024 token）超过 512 预算，后 8 个排队 1 个 iteration；运行中偶尔两个请求同时到达也会造成同样的 1 步等待。
  - `C=8 long_prefill`：峰值 3、均值 0.62、**24.9% 的活跃时间有排队**。这是结构性的：512-token prefill 在 8 条 decode 之后只剩 504 的预算，必须分两块；一块在算时，后面的请求只能等（`scheduler.py:196,218,333-338`）。这也是它 ITL 尾巴（>6 ms 占 28%）的同一个根因。
- `C=32` 的 waiting 采样为 0，但**不能据此断言没有排队**：活跃窗口只有 3.12 s、7 个样本，而启动时的 32 个并发 prefill 必然造成几十毫秒级的排队，0.5 s 采样几乎一定漏掉（§6.1 分辨率警告）。
- 采样口径提醒：0.5 s 采样**可能漏掉短于 0.5 s 的排队**；但 TTFT 在 r=10 的 p95 只有 31.5 ms，从客户端侧排除了「有长期隐藏队列」的可能。

### 6.4 KV 与抢占：4.2% 用量，且结构上不可能抢占

**先把块数反解出来（B 级推断）**：12 个文件的 KV 峰值都是 `1/8925` 的整数倍（C=32 因采样只取到 377/384）：

| C=1 | 0.13445% | 12.0 | 12 | 192 | 1×192 ✅ |
| C=2 | 0.26891% | 24.0 | 24 | 384 | 2×192 ✅ |
| C=4 | 0.53782% | 48.0 | 48 | 768 | 4×192 ✅ |
| C=8 | 1.07563% | 96.0 | 96 | 1,536 | 8×192 ✅ |
| C=16 | 2.15126% | 192.0 | 192 | 3,072 | 16×192 ✅ |
| C=32 | 4.22409% | 377.0 | 377 | 6,032 | ≈32×192=6,144 |
| C=8 balanced | 2.15126% | 192.0 | 192 | 3,072 | 8×384 ✅ |
| C=8 long_prefill | 2.95798% | 264.0 | 264 | 4,224 | ≈8×528 |
| r=2 | 0.52661% | 47.0 | 47 | 752 | — |
| r=5 | 0.56022% | 50.0 | 50 | 800 | — |
| r=10 | 1.05322% | 94.0 | 94 | 1,504 | — |
| r=20 | 2.00560% | 179.0 | 179 | 2,864 | — |

`C=8: 96 块 = 1,536 token = 8×192`、`balanced: 192 块 = 3,072 = 8×384` —— **逐请求精确**。由此可得：

- **KV 池 = 8,925 块 = 142,800 token**（块大小 16 由 day5 的 9,029 块 / 144,464 token 推得，`day5_piecewise_server.log:36`）。
- day6 比 day5 少 104 块（−1.15%），方向与「`max-num-batched-tokens` 256→512 / 更大的 CUDA graph 池需要更多显存」一致，但**没有 day6 server log，无法归因**（C 级）。
- 峰值用量只占 **4.22%**（C=32），全组从未超过 5%。

**为什么抢占不可能（B 级）**：抢占只在 `allocate_slots()` 返回 `None` 时发生（`scheduler.py:252-284`），也就是 KV 块耗尽时。而

```
max_num_seqs(32) × max_model_len(1024) = 32,768 token = 2,048 块 < 8,925 块
```

即**即使 32 个槽位全部跑满 1024 token，也只用掉 23% 的 KV**。所以本轮的 `preemptions = 0` 不是「运气好」，而是配置决定的**结构性质**。这条对理论题「哪些现象不能直接归因于 KV 不足」很关键：**在这里，抢占数恒为 0 完全不能用来证明系统健康**，它只是说明 `max-num-seqs × max-model-len` 远小于 KV 池。

## 8. 能得出 / 不能得出

**能得出：**

1. **在这套配置下，把并发从 1 推到 32，吞吐涨 23.3×（248.8→5,796 tok/s），E2E 只涨 36%**；瓶颈从「固定开销」变成了「TTFT 与 prefill 排队」，而不是 decode 算力。
2. **TTFT 是并发的第一成本**：13→59 ms（p95 110 ms），且主要由「prefill 与 decode 合批」和「启动时 C 个 prefill 分批」决定；开环到达模式下 TTFT 几乎不随负载涨。
3. **ITL 尾部与在途数不单调**：C=32 的 ITL p95（6.94）好于 r=20（13.04）和 long_prefill（12.31）；`long_prefill` 的 512-token prompt 撑爆 512-token 预算，是唯一一组「waiting>0 + ITL 尾巴暴涨」的负载。
4. **配置的 SLO（200/15）没有区分力**：12 组全部 100% 达标，goodput 恒等于吞吐；但把 SLO 收紧到 50/6、30/5 后，goodput 峰值从 C=32 依次左移到 C=16、C=8 —— 这组数据可以实证「最大吞吐 ≠ 最大 goodput」。
5. **KV 与抢占完全不是限制**：峰值 4.22%、0 抢占，且这是 `max-num-seqs × max-model-len < KV 池` 的结构结果。
6. **两条测量链（客户端流式计时 / 服务端 counter）在长运行上互相校验到 ±1.7%**，token 计数还能精确对上「+1 个预热请求」，说明采集可信。

**不能得出（本次未覆盖）：**

1. **GPU 的饱和吞吐**：按 README，C=32 是 `max-num-seqs` 的上限，不是排队饱和点；把 `max-num-seqs` 调到 64 或把开环 λ 推到 40+ 才能看到拐点，本次没有。
2. **排队主导区的延迟形状**：除了 long_prefill 的少量排队（峰值 3），没有任何一组进入「waiting 持续增长」的状态；TTFT 的排队段、goodput 的崩塌段都没测到。
3. **>32 并发的 goodput 曲线**：`max-num-seqs=32` 之外完全没有数据，「最大 goodput」只能报「本次观测到的最大 45.28 req/s」。
4. **ITL 尖峰的精确归因**：chunk 合并与 prefill 插入在客户端数据里不可区分；要分开必须有服务端每 iteration 的时间戳或 trace。
5. **跨模式的同条件对比**：r=20 与 C=16/32 的差异（TPOT +24%、ITL p95 +88%）可能是到达模式效应，也可能只是单次运行间的抖动；每组只跑 1 次，无法区分。
6. **重复性与置信区间**：每组 1 次、128 请求，p99 就是第 2 名；跨组的 ±2–5% 差异不能区分「负载效应」和「运行间抖动」。
7. **prefill 的 GPU 侧代价**：没有 nsys/ncu/GPU 利用率，无法验证「512-token 预算是 long_prefill 的唯一约束」还是也有 GPU 计算瓶颈。
8. **真实用户模型**：闭环是零思考时间，开环没有客户端退避；两者都不是生产流量。
